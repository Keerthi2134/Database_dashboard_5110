The many-to-many relationship between RIDER and STAGE is handled through the RESULT 
relation. Each result connects one rider to one stage with the foreign keys. The composite 
primary key, {bib_number, stage_id}, allows every rider to have results recorded for multiple 
stages and each stage to have results for multiple riders . This prevents duplicate results for 
the same rider-stage pair at the same time.  
 
The following SQL code translates the relations in Table 1 into `CREATE TABLE` statements, 
including their primary keys, foreign keys, and constraints that can be defined directly in SQL. 
 
CREATE TABLE country ( 
    country_code CHAR(3) PRIMARY KEY, 
    country_name VARCHAR(100) NOT NULL, 
    CHECK (country_code ~ '^[A-Z]{3}$') 
); 
 
CREATE TABLE team ( 
    team_name VARCHAR(100) PRIMARY KEY, 
    country_code CHAR(3) NOT NULL, 
    FOREIGN KEY (country_code) REFERENCES country(country_code) 
); 
 
CREATE TABLE rider ( 
    bib_number INTEGER PRIMARY KEY, 
    rider_name VARCHAR(100) NOT NULL, 
    dob DATE NOT NULL, 
    role VARCHAR(50) NOT NULL, 
    is_leader BOOLEAN NOT NULL, 
    team_name VARCHAR(100) NOT NULL, 
    country_code CHAR(3) NOT NULL, 
    FOREIGN KEY (team_name) REFERENCES team(team_name), 
    FOREIGN KEY (country_code) REFERENCES country(country_code) 
); 
 
CREATE TABLE location ( 
    location_name VARCHAR(100) PRIMARY KEY, 
    country_code CHAR(3) NOT NULL, 
    FOREIGN KEY (country_code) REFERENCES country(country_code) 
); 
 
CREATE TABLE stage ( 
    stage_id INTEGER PRIMARY KEY, 
    stage_date DATE NOT NULL, 
    distance_km NUMERIC(5, 2) NOT NULL, 
    stage_type VARCHAR(30) NOT NULL, 
    start_location VARCHAR(100) NOT NULL, 
    finish_location VARCHAR(100) NOT NULL, 
    FOREIGN KEY (start_location) REFERENCES location(location_name), 
    FOREIGN KEY (finish_location) REFERENCES location(location_name), 
    CHECK (distance_km > 0), 
    CHECK (stage_type IN ( 
        'flat', 'hilly', 'mountain', 'individual time-trial' 
    )), 
    CHECK (start_location <> finish_location) 
);

CREATE TABLE result ( 
    bib_number INTEGER NOT NULL, 
    stage_id INTEGER NOT NULL, 
    rank INTEGER NOT NULL, 
    finish_time INTEGER NOT NULL, 
    bonus INTEGER NOT NULL DEFAULT 0, 
    penalty INTEGER NOT NULL DEFAULT 0, 
    PRIMARY KEY (bib_number, stage_id), 
    FOREIGN KEY (bib_number) REFERENCES rider(bib_number), 
    FOREIGN KEY (stage_id) REFERENCES stage(stage_id), 
    CHECK (rank > 0), 
    CHECK (finish_time >= 0), 
    CHECK (bonus >= 0), 
    CHECK (penalty >= 0) 
); 
 
CREATE VIEW result_with_adj_time AS 
SELECT 
    bib_number, 
    stage_id, 
    rank, 
    finish_time, 
    bonus, 
    penalty, 
    (finish_time - bonus + penalty) AS adj_time 
FROM result; 
 
CREATE TABLE exit ( 
    bib_number INTEGER PRIMARY KEY, 
    stage_id INTEGER NOT NULL, 
    reason VARCHAR(255) NOT NULL, 
    FOREIGN KEY (bib_number) REFERENCES rider(bib_number), 
    FOREIGN KEY (stage_id) REFERENCES stage(stage_id) 
); 
 
CREATE TABLE award ( 
    award_id INTEGER PRIMARY KEY, 
    award_name VARCHAR(100) NOT NULL, 
    bib_number INTEGER, 
    team_name VARCHAR(100), 
    FOREIGN KEY (bib_number) REFERENCES rider(bib_number), 
    FOREIGN KEY (team_name) REFERENCES team(team_name), 
    CHECK ( 
        (bib_number IS NOT NULL AND team_name IS NULL) 
        OR 
        (bib_number IS NULL AND team_name IS NOT NULL) 
    ) 
);

The adjusted time (adj_time) is a derived attribute calculated as finish_time − bonus + penalty. 
Instead of storing it in the RESULT table, we create a SQL view named result_with_adj_time 
to calculate it dynamically. This avoids redundant data storage and ensures that adjusted time 
reflects any changes to finish_time, bonus, or penalty.

Functional Dependency Identification 
We identified the functional dependencies based on the primary keys, relationships, and 
business rules defined in Table 1. 
1. COUNTRY: country_code → country_name because each country code uniquely 
identifies one country and its name. 
2. TEAM: team_name → country_code because each team has a unique name and 
belongs to exactly one country. 
3. RIDER: bib_number → rider_name, dob, role, is_leader, team_name, country_code 
because each rider has a unique bib number that determines their personal 
information, team, and country they are representing.   
4. LOCATION: location_name → country_code because each location has a unique 
name and belongs to one country. 
5. STAGE: stage_id → stage_date, distance_km, stage_type, start_location, 
finish_location because each stage has a unique identifier that determines its date, 
distance, type, and start and finish locations. 
6. RESULT: (bib_number, stage_id) → rank, finish_time, bonus, penalty because each 
rider can have at most one result per stage. Therefore, both attributes are required to 
uniquely determine the result. 
7. EXIT: bib_number → stage_id, reason because each rider can exit the race at most 
once, so their bib number determines the exit stage and reason. 
8. AWARD: award_id → award_name, bib_number, team_name because each award 
has a unique identifier that determines its name and the corresponding rider or team 
receiving it. 
After identifying the functional dependencies, we derived the minimal cover by splitting 
dependencies with multiple right -hand-side attributes into individual dependencies. We then 
checked for redundant dependencies to ensure that each remaining FD was necessary. 
Although bib_number → country_code in the RIDER relation and award_id → team_name in 
the AWARD relation may appear redundant when considering relationships across the entire 
database, we retain both dependencies in their respective minimal covers. Function al 
dependencies are evaluated within each relation based on its attributes and business rules. 
In RIDER, country_code represents the rider's nationality, which cannot necessarily be 
derived from team_name , as a rider may represent a different country from their team. 
Similarly, in AWARD, an award may be assigned directly to a team rather than an individual 
rider, so team_name cannot always be derived through bib_number. Therefore, neither 
dependency can be  inferred from the other dependencies within its respective relation, and 
both must be retained in the minimal cover.

All relations satisfy 1NF because each attribute contains a single value. They also satisfy 2NF: 
relations with a single -attribute candidate key have no partial dependencies, while the non -
key attributes in RESULT depend on the complete key (bib_number, stage_id).  
Based on the identified functional dependencies, the LHS of every FD in the minimal cover is 
a candidate key and therefore a superkey. Thus, the final relations satisfy BCNF and 
consequently also 3NF . Country, team, rider, stage, and location details are stored in 
separate relations to reduce repetition and update anomalies. The derived attribute adj_time 
is calculated through a view rather than stored in RESULT  to avoid redundancy . Therefore, 
no further decomposition is required under the stated functional dependencies.
